# awesome-claude

Read [`README.md`](README.md) first. Edit `mods/`, never `plugins/`
(generated by `bun build.ts`).

The kit the mods draw with (`@kit/…`), its design rules, the engine's limits
and the browser bench live in zen (`github:satoramoto/zen`,
`src/harness/claude-code/`; reference:
[`docs/harness-claude-code.md`](https://github.com/satoramoto/zen/blob/main/docs/harness-claude-code.md)),
pinned in `package.json` as `"@satoramoto/zen": "github:satoramoto/zen#<sha>"`.
To change the kit, change it in zen, then raise the pin here (`bun install`,
`bun build.ts`, bump the mods whose `plugins/` changed). While working on both,
`ZEN=~/Code/satoramoto/zen bun build.ts` (and `bun run watch`, `playground`,
`storybook` with `ZEN` set) takes the kit and bench from that checkout instead;
rebuild from the pin before committing `plugins/`. `zen.ts` finds the folder.

Skills for working here, in `.claude/skills/`:
[`mod-authoring`](.claude/skills/mod-authoring/SKILL.md) (making or changing a mod),
[`storybook-prototyping`](.claude/skills/storybook-prototyping/SKILL.md) (how it looks),
[`headless-verification`](.claude/skills/headless-verification/SKILL.md) (checking it works).
For the engine's API itself, the engine's `plugin-authoring` skill.

Run `bun install` once in a fresh clone or worktree.

**A change** runs `bun build.ts` and `bunx tsc -p plugins/<mod>` for the mod
it touched, then commits. Nothing else. Validate and tests are their own step,
a test pass you run when asked or before a PR, and CI runs everything on the
PR. Version bumps and the changelog also happen once, when the PR is opened
(see below), not on every commit.

| Command | What it checks | When to run |
| --- | --- | --- |
| `bun build.ts` | the mods compile into `plugins/`, zen's kit copied in | after any change under `mods/` or to the zen pin |
| `bun run watch` (`bun build.ts --watch`) | the same, again on every save | while working, with the mods loaded in a session |
| `bunx tsc -p plugins/<mod>` | the compiled mod, tests included, type-checks (needs the engine's types in `plugins/<mod>/.claude-plugin/types/`, laid when the mod loads; see `headless-verification`) | after any `.ts`/`.tsx` change |
| `claude plugin validate plugins/<mod>` | the engine accepts the compiled mod: its hooks, calls, state reads and writes against its contract | test pass; after a state-contract change |
| `claude plugin validate .` | the marketplace (`.claude-plugin/marketplace.json`) lists every `plugins/` folder with matching versions | when opening a PR (after the bumps) |
| `claude plugin test plugins/<mod>` | the mod's `*.test.ts`: its panes mounted on each surface through the engine's test kit, acted on and read | test pass only |
| `bun run playground` | whole mods drawn in the browser from their own render hooks and sample data; runs `bun build.ts` and `claude plugin validate` on each save | while wiring up a mod |
| `bun run storybook` | each mod scenario as a story, drawn by zen's bench; surface, theme, frame and width in the toolbar (the kit's own stories are in zen's Storybook) | while designing how something looks |

`bun run playground` and `bun run storybook` take their port from `PORT`
(5173 and 6006 by default).

Tests are written to a spec, as their own step, not alongside a change: the
behaviours a mod promises, with cases enumerated from their boundaries
(partitions and edges, each surface, state transitions, failure paths). They're
render and behaviour tests through the engine's test kit (`claude-code/testing`):
mount the mod's component on the terminal and the desktop and check what it
draws and what its buttons do. Don't write tests that restate a function's
code or pin details the spec doesn't promise.

A new mod appears in `plugins/` only after `bun build.ts`, and needs an entry
in `.claude-plugin/marketplace.json` (`name`, `source: ./plugins/<mod>`,
`description`, `version`). When a PR is opened, every mod whose compiled output
(`plugins/<mod>/`, so a new zen pin that changes the kit too) differs from the base gets its
version raised once above the base's, in its `plugin.json` and in
`.claude-plugin/marketplace.json`, with one `CHANGELOG.md` entry for the PR.
Marketplace installs only update when the version changes, and CI fails a PR
that changes a mod's output without raising its version above the base's, or
whose two versions differ. Don't bump on every commit.

## Design rules

The mods look like an instrument inspector (details in zen's doc, "The
inspector: design rules"): collapsible header rows with readings indented under
them (label, thin flat gauge, value, unit); no bubbles, panels, outlines or game
words; bars rounded only by SVG end caps. Colours only from the kit's
`tokens.ts` (`@kit/tokens`), each with its one meaning. Draw with the kit's
`ui.tsx` components (`@kit/ui`) rather than raw boxes and colours. Truncate text (`wrap="truncate"`, `minWidth={0}` on the boxes around
it) rather than letting it overflow.

## CI and PRs

CI ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) runs on every PR: the
build (and fails if `plugins/` wasn't rebuilt and committed), `claude plugin
validate` for every mod, `claude plugin test` for every mod that has a
`*.test.ts` or `*.test.tsx`, `claude plugin validate .` for the marketplace, and
on a PR, that every existing mod whose `plugins/<mod>/` changed has a higher
version than the base's.
Work on a branch, open a PR, and let CI be the final check; `main` takes PRs
only. Every PR gets auto-merge turned on when it's opened (`main` requires the
CI check, so it merges once CI passes).

Every agent commit ends with a blank line and a co-author trailer naming the agent
that made it, for example `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
